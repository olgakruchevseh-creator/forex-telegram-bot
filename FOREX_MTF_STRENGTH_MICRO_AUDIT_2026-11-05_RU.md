# Forex-бот · аудит валютной силы, согласования сигналов и журналов

**Дата:** 05.11.2026  
**Основа:** присланный `forex-telegram-bot-main (1).zip` (533 файла внутри проекта, без корневого каталога).  
**Результат:** самостоятельный патч изменённых/новых файлов, а не полная замена проекта.

## 1. Что установлено по исходному коду

1. В брифинге действует отдельная матрица `briefing_strength_verified.py`: 7 USD-мажоров, общая закрытая H1, лог-доходности за 1/4/12/24 H1 с весами 15/35/30/20, условный индекс 0–100. **Это не процент вероятности сигнала.** Она не равна более старому расчёту `analysis.py` / `STRENGTH_LOOKBACK=4`, который используют торговые подсистемы. Поэтому «верная цифра в брифинге» ещё не гарантирует одинакового решения всех модулей.
2. Найдены места, где *прежняя* H1-сила влияла на допуск кандидата: `signal_context.py` (откат), `master_direction.py` (штраф качества / AMD-ветка) и ряд сканеров (`patterns.py` — гармонические фигуры, `silver_bullet_ict.py`, `levels.py`, `order_block.py`, `breaker_block.py`, `fib_smc.py`, `retest_confirmation.py`, и др.). Эти независимые проверки могли отсечь паттерн **до** Forex Killer и финальной матрицы.
3. В конфликте LONG и SHORT одной пары `signal_context.prepare` использовал силу в непосредственном сравнении (`directed_gap * 10 + junior_n`). Это была дополнительная скрытая возможность выбрать одну сторону за счёт силы, даже если структура противоречит ей.
4. Часть модулей давала положительную добавку к качеству через `abs(gap)` после положительной проверки силы. После ослабления старого veto противоположная сила могла бы ошибочно **повысить** оценку. Такие бонусы изменены на направленные, `max(0, gap * сторона)`.
5. Отчётный показатель **«Сначала движение в пользу сигнала: 33%»** не измерял первую реакцию цены. Старый алгоритм сравнивал индексы H1 максимумов MFE/MAE; при обоих максимумах в одном H1 реальная последовательность неизвестна. Значит, из числа 33% нельзя сделать вывод о числе действительно «хороших первых движений».
6. «Лучший модуль» / «лучшая пара» в дневном журнале выбирались по **балансу числа TARGET и INVALIDATED**, а не по достоверно лучшей доле успехов с учётом размера выборки. Для Patterns это особенно важно: название «лучший» без `n` может вводить в заблуждение.
7. Архив не содержит полного исторического состояния шести сигналов от 04.11.2026 и их свечных снимков в момент входа; находятся лишь отдельные записи журнала решений от 05.11.2026. Восстановить причины всех трёх TARGET, двух отмен и одного 8-часового завершения **невозможно из этого ZIP**. Никакие обещания улучшить реальную результативность проверкой кода не подтверждены.

## 2. Что изменено

### Новый отдельный многотаймфреймовый слой

Добавлен `multi_tf_currency_strength.py`. На каждом кандидате по общим данным Twelve Data вычисляется **независимый** снимок:

| Таймфрейм | Длина изменения | Устойчивость | Максимальный допустимый возраст закрытой свечи |
|---|---:|---:|---:|
| W1 | 4 закрытые недели | 3 последних закрытых окна | 12 суток |
| D1 | 5 закрытых дней | 3 окна | 4 суток |
| H4 | 6 закрытых H4 | 3 окна | 12 часов |
| H1 | 4 закрытых H1 | 3 окна | 3 часа |

Алгоритм: 100 × ln(Pпоследняя/Pранняя), переворот знака для USD/XXX, затем центрирование восьми валют так, чтобы их баллы суммировались в нуль. **Это относительные лог-изменения в процентных пунктах, НЕ вероятность и НЕ предсказание.** Пара сравнивается через разность баллов базовой и котируемой валют. Поддержка/конфликт проверяется с небольшими экспериментальными зонами нейтральности: W1 0.12, D1 0.08, H4 0.05, H1 0.03 лог-п.п. Эти пороги требуют независимой калибровки по истории; они не оптимизированы под прибыль.

Особые защиты:
- Только **закрытые** свечи; якорь снимка — закрытие сигнальной H1, а не любое более позднее время опроса. Незакрытый W1/D1/H4 не используется.
- Проверка всех 7 валютных пар на **идентичные временные метки** внутри данного таймфрейма. Нельзя смешивать сегодняшние EUR/USD с вчерашними USD/JPY.
- Пропуски, несинхронные, старые, дублирующиеся свечи, нечисловые и неположительные котировки дают **«НЕТ ДАННЫХ»**, а не ложный ноль или «сила подтверждает».
- Результат имеет `decision_authority=false`, `can_block_signal=false` и передаётся в общий контекст, Telegram-карточку и журнал решений.
- Используются уже загруженные W1/D1/H4/H1 для семи USD-мажоров: **дополнительных API-вызовов не добавлено**.

### Без самостоятельного запрета по силе

В `config.py` добавлен явный переключатель:

```python
CURRENCY_STRENGTH_ADVISORY_ONLY = True
```

По умолчанию старые *изолированные* блокировки по валютной силе в просмотренных сигнальных путях переведены в наблюдение; сохранены иные проверки — закрытие H1, старшая структура, подтверждение младших ТФ, риск позднего входа, ловушки, новости, корректность целей. Возврат `False` позволяет сравнить старую логику в контролируемом replay (новые W1/D1/H4/H1-наблюдения при этом останутся).

Конфликтные LONG/SHORT одной пары теперь сравниваются по структурным признакам (согласование H4 ZigZag, старших TF, младших TF, исходное качество), а не по `directed_gap` как ключевому арбитру. При выключенном advisory восстанавливается прежняя формула выбора стороны.

**Ограничение:** это не удаление всей валютной силы из каждого возможного старого *мягкого* score, примеры — `echo_projection.py` и несколько других дополнительных контекстов. Старое значение может оставаться слабой частью совокупной оценки, а новая MTF-оценка — полностью диагностическая. Для строгого утверждения «сила никак не влияет на финальный score» потребуется отдельный полноконтурный replay всех генерирующих путей.

### Журнал

- `decision_journal.py` сохраняет `currency_strength_mtf` в `context_gate` для событий воронки, включая разрешённые и заблокированные (при наличии свечных данных).
- `signal_journal.py` **не считает** экстремумы MFE/MAE внутри одной H1 доказательством порядка их достижения (`None` — неопределённо). Текст дневного/недельного отчёта теперь корректно называет показатель «Пик MFE раньше пика MAE (разные H1)», указывает число сравнимых случаев и неопределённых H1.
- Вместо некорректного звания «лучшего» показываются **лидер по балансу целей и отмен**, размер выборки, число TARGET/INVALIDATED и сам баланс.
- Стандартные TARGET/INVALIDATED по ATR **не подменяют** реальную отработку зафиксированных TR1/TR2/TR3, комиссии, спред и исполнение.

## 3. Проверки и статус

- Синтаксис проекта: `python -m compileall -q .` — **успешно**.
- Основной набор без четырёх тестовых файлов, требующих отсутствующую библиотеку Telegram: **885 passed** (уточнить финальный счёт при упаковке), ошибок нет.
- Четыре файла `test_integration_consistency.py`, `test_master_direction.py`, `test_runtime_silence_recovery.py`, `test_scanners.py` **не исполнены** в данном контейнере: импорт `bot.py` требует `python-telegram-bot`, а пакет `telegram` отсутствует. Это **ограничение среды проверки**, не доказательство успешной интеграции.
- Протестированы знаки USD/XXX, стабильность W1/D1/H4/H1, пропущенные и несинхронные данные, устаревшие H1, игнорирование незакрытых свечей, исторический якорь времени, конфликт старшего ТФ и альтернативный режим арбитража.
- Не выполнялись: запросы к **живой** Twelve Data, отправка Telegram, тесты в Railway, реальное воспроизведение шести сигналов 04.11 и out-of-sample A/B-эксперимент. Поэтому изменение доли прибыльных сделок, частоты сигналов и правильности новых сигналов **не подтверждено**.

## 4. Безопасный порядок внедрения

1. Сделайте резервную копию текущего GitHub/Railway состояния. Внести **содержимое малого ZIP** поверх соответствующих путей в корень Forex-репозитория; остальные файлы оставить нетронутыми. Архив специально содержит только изменённые/новые файлы (с сохранением `forex-telegram-bot-main/` как корня).
2. В рабочей среде установить зависимости: `pip install -r requirements.txt`. В проекте требуется `python-telegram-bot[job-queue]==22.8`; дополнительных зависимостей для нового расчёта не нужно.
3. Запустить все тесты **включая четыре интеграционных**, проверить закрытия W1/D1/H4/H1 у реального поставщика, часы сессий, журнал блокировок, отсутствие поздних сигналов и формат Telegram-карточки.
4. Сначала вести минимум одну–несколько недель параллельный журнал и затем исторический replay старого и нового режимов на одних и тех же свечных данных. Сравнивать TARGET/INVALIDATED, TR1/2/3, MFE/MAE, число сигналов, поздние входы и ошибки данных **для каждого модуля**.
5. Если поток стал слишком шумным, **вернуть предыдущий ZIP**; для локального сравнения старых блокировок можно временно поставить `CURRENCY_STRENGTH_ADVISORY_ONLY = False` и повторить тесты.

## 5. Приоритет следующих проверок

- Верифицировать у Twelve Data **метки открытия недельных свечей**, торговый календарь праздников и свежесть W1 при начале недели. Новый алгоритм исходит из того, что timestamp — начало свечи в UTC, а закрытие W1 наступает через семь суток; при специфичных метках провайдера будет честный статус «НЕТ ДАННЫХ», но потребуются поправки календаря.
- Для действительной метрики «куда цена пошла первой» необходимо запрашивать и воспроизводить M5/M15 после входа с контролем одновременного достижения уровня и стопа, а не сравнивать H1-экстремумы.
- На большой выборке проверить не только Patterns, но каждый другой модуль; особенно выяснить, сколько хороших кандидатов ранее отвергались **исключительно** по strength-only причинам.
- Не считать низкий результат тестов или статистику одного дня основанием менять риск, позицию или торговый порог без воспроизведения с издержками.
