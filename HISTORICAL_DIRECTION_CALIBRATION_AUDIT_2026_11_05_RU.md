## 2. Математический аудит: сравниваем три, а не две формулы

| Обозначение | Метод | Цель |
|---|---|---|
| `old_simple_4h` | `analysis.currency_strength`: обычная процентная доходность `100 × (close_t / close_t-4 − 1)`; вклад USD усреднён по семи парам, остальных валют — по одной; потом из значений вычтено среднее | Повторить **оригинальный торговый** метод без изменения порогов |
| `new_log_4h` | Логарифмическая доходность `100 × (ln(close_t) − ln(close_t-4))`, точное zero-sum USD-star распределение | Изолировать влияние **самой математической формулы** при одинаковых 4 H1 |
| `new_log_blend` | Лог-доходности 1/4/12/24 H1 с весами 0.15/0.35/0.30/0.20 и тем же zero-sum решением | Измерить влияние **другого горизонта** в актуальном брифинге |

**Критически важная особенность:** в корзине, состоящей **только из семи USD-пар**, zero-sum решение точно удовлетворяет равенству `S(base) − S(quote) = логарифмическая доходность именно этой пары` для соответствующего горизонта. Следовательно, новая сила не является независимым дополнительным сигналом для той же пары, а отображает её собственный momentum (с общей системой ранжирования валют). Нельзя выдавать корреляцию этих величин за два независимых подтверждения рынка. Старый алгоритм, напротив, добавляет связанную с остальными USD-парами составляющую через особую нормализацию USD.

**Математическая эквивалентность старой формулы:** тест сравнивает реконструкцию на каждом префиксе со штатной функцией `analysis.currency_strength`; тест пройден. Новые расчёты используют существующее ядро `currency_strength_math`, а не придуманную отдельную трактовку.

## 3. Что добавлено

`historical_direction_calibration.py` — независимый CLI без подключений к торговому сканеру, Telegram, Master и Railway scheduler:

1. **Выгрузка:** по явному запросу читает `TWELVE_DATA_API_KEY` из окружения и запрашивает **семь пар** H1 через Twelve Data. Ограниченный тариф может отказать в истории. Не выводит секрет в логи. Если хотя бы одна серия недоступна, не подменяет её нулями. Выгрузка осуществляется во временную папку и принимается только после проверки семи файлов.
2. **Импорт:** читает CSV с временем ОТКРЫТИЯ H1 в **UTC**. Проверяет все OHLC, повторные/некорректные временные метки и отсутствие незакрытых/будущих H1. Не объединяет корзину при отсутствии общих 26 закрытых H1.
3. **Replay:** три расчёта выполняются по одному и тому же **историческому префиксу** до закрытия H1 включительно. Будущие свечи используются **только** для оценки последующего исхода, а не для построения прогноза.
4. **Хронологическое разделение:** 70% ранних часов — подбор/обучение (если включён флаг), 30% поздних — out-of-sample; между ними защитный буфер **8 H1**. Любой подбор порога — только на обучении; по умолчанию применяется один фиксированный порог `0.025 п.п.` для всех методов.
5. **Метрики:** направление цены через 1/2/4/8 следующих H1, доля предсказанных случаев, среднее движение в сторону/против в ATR14, диагностическое первое касание +1 ATR или −0.75 ATR, случаи неоднозначного касания и время без достижения. Есть парное сравнение методов на **одинаковых** H1-парах и грубая оценка смены знака H1 с продолжением через 2 часа.
6. **Ограничения:** оценки не пересекают **местную календарную дату Europe/Amsterdam** (для внутридневного стиля) и не используют отсутствующие часы как последовательные H1. Порог при отсутствии данных не меняет живые сигналы. Контрольные суммы SHA-256 каждого CSV сохраняются рядом с результатами для воспроизводимости.

**Осторожно с интерпретацией:** вход по закрытию H1 — расчётная условность. В реальной торговле цена входа будет другой, возможны спред/проскальзывание. Цель и отмена +1/−0.75 ATR — **стандартные диагностические уровни журнала**, не настоящие TR1/TR2/TR3 конкретного сигнала. Если High и Low одной свечи одновременно пересекают оба порога, событие считается **неоднозначным**; хронологию внутрисвечного движения по H1 восстановить нельзя. Повторяющиеся часы и пары сильно коррелированы.

## 4. Как получить реальные результаты, не передавая ключ API в чат

В папке Forex-репозитория, где установлен Python и доступен уже настроенный в Railway ключ `TWELVE_DATA_API_KEY`, можно выполнить:

```bash
python historical_direction_calibration.py fetch --data-dir ./fx_history_h1 --start-date 2026-05-01 --end-date 2026-11-04
python historical_direction_calibration.py evaluate --data-dir ./fx_history_h1 --out ./fx_calibration_results
```

Это создаст семь CSV и затем два отчёта в `./fx_calibration_results/`:

```text
calibration_results.json
calibration_report_RU.md
```

Для дополнительной **экспериментальной** подстройки порога только на первом отрезке:

```bash
python historical_direction_calibration.py evaluate --data-dir ./fx_history_h1 --out ./fx_calibration_results --tune-on-train
```

**Дату конца выбирайте не позднее последнего закрытого H1**. Программа сама исключает ещё открытую свечу при получении данных. Ограничение API и поддержка указанного диапазона зависят от подписки. По официальной документации Twelve Data, с `start_date` + `end_date` не следует одновременно передавать `outputsize`, иначе выборка будет искусственно усечена: https://support.twelvedata.com/en/articles/5656039-how-to-get-historical-prices . Для полугодовой H1-истории предел в 5000 свечей обычно не должен достигаться, но если источник возвращает 5000, загрузка остановится и попросит разделить период, чтобы избежать скрытого усечения.

**Не помещайте CSV-историю, API-ключи и Telegram-токены в публичный GitHub.** На Railway файлы в контейнере могут исчезнуть при повторном деплое, если путь не расположен на постоянном Volume. Файлы истории и результаты можно сохранить локально или на отдельном Volume. Нельзя передавать в чат настоящий API-ключ; он читается из окружения.

Вариант без доступа к API: загрузить семь исторических CSV с названиями `EURUSD_H1.csv`, `GBPUSD_H1.csv`, `USDJPY_H1.csv`, `USDCHF_H1.csv`, `AUDUSD_H1.csv`, `NZDUSD_H1.csv`, `USDCAD_H1.csv`. Требуются пять столбцов `datetime,open,high,low,close`; `datetime` означает начало H1 в UTC, а свечи должны быть полностью закрыты.

## 6. Что разумно делать после получения исторических данных

1. Воспроизвести все три метода на одинаковых закрытых H1; сравнить результат в каждой паре и в каждой сессии. Если новая формула выигрывает только на обучении, но не на отложенном периоде, **не менять боевой вариант**.
2. Добавить реальные точки решений из `decision_journal.jsonl` и `decision_replay.jsonl` (они не включены в нынешний ZIP), чтобы отделить механическую угадываемость часа от качества **фактически отправленных сигналов** и отклонённых кандидатов.
3. Для ZigZag, Echo, Next Pivot и новостных реакций получить датированные снимки **на момент решения**; не оценивать прошлую картинку по перерисованному будущему графику.
4. Отдельно проверять смену режима/откат/разворот W1/D1/H4/H1 на синхронной истории всех необходимых TF; H1-математический A/B-тест **не равен** полноценному тесту этих модулей.
5. Только после достаточной оценки вне обучающей выборки и учёта издержек согласовать новые пороги в боевом боте отдельным патчем. Нельзя автоматически подменять старые пороги новыми из диагностического replay.
